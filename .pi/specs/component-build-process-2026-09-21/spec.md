# Feature Spec: Component Build Process

- Status: draft
- Date: 2026-09-21
- Interview: `interview-guide.md`
- Research: `TODO.md` (API doc conventions)

## Problem

Component specs in `handy-ds` are too verbose, no API documentation is produced for agents that build client apps, and too many visual/theming decisions are left for the building agent to assume. When a new component is built from a Base UI primitive, there is no repeatable way to decide what Base UI props to expose, what new props to add, and how those props map to semantic tokens.

## Goal

A repeatable, two-phase process that produces, for every Base UI-derived component, (1) a concise internal spec and concise outward-facing API documentation, (2) matching code and Figma artifacts, and (3) an owner-facing MDX docs page with live examples for every visual axis/prop. The process gives building agents just enough context and no more.

## Requirements

### Process shape

- WHEN a new Base UI-derived component is started
  THE SYSTEM SHALL run Phase 1 before any component code is written.
- WHEN Phase 1 completes
  THE SYSTEM SHALL produce a per-component interview guide, an internal component spec, and an outward-facing API doc entry.
- WHEN Phase 2 starts
  THE SYSTEM SHALL consume only the approved Phase 1 internal spec (not the API doc).
- WHEN a component is accepted
  THE SYSTEM SHALL have matching code, Figma artifacts, and owner-facing MDX docs derived from the same spec.

### Phase 1 — Spec & Document

- WHEN the per-component interview begins
  THE SYSTEM SHALL list every Base UI prop and behavior, present each to the user with a short description, and record which are exposed, renamed, wrapped, or omitted.
- WHEN the exposed Base UI surface is set
  THE SYSTEM SHALL propose extension/additional props and let the user add, remove, or modify them.
- WHEN the prop set is approved
  THE SYSTEM SHALL define each prop in detail and map it to semantic tokens from the `hds/sem/...` namespace.
- WHEN the internal spec is written
  THE SYSTEM SHALL keep it complete and nothing more: a description with do/don't usage statement (~3 sentences), Base UI API surface, extension API surface, and per-prop token mapping sections.
- WHEN the API doc is written
  THE SYSTEM SHALL follow the researched API doc conventions (see Research), include a usage statement, a combined prop/extended-prop table with per-value definitions where needed, and SHALL NOT mention Base UI or list omitted Base UI props.

### Phase 2 — Build (Code, Figma, and Owner Docs)

- WHEN component code is built
  THE SYSTEM SHALL use only the approved internal spec and existing token system as inputs, follow `docs/component-conventions.md`, consume only `hds/sem/...` tokens, and SHALL NOT reference drivers or primitives directly.
- WHEN the Figma component is built
  THE SYSTEM SHALL be hand-built by the user or generated by an agent from the same spec, and its visual states SHALL match the code.
- WHEN owner docs are built
  THE SYSTEM SHALL run after component code exists so live examples render, document every visual axis/prop from the spec with a live example per value, and produce `docs/components/<component>.mdx`.

### Constraints

- WHEN a component is specced
  THE SYSTEM SHALL record the Base UI version it was documented from.
- WHEN a component is built
  THE SYSTEM SHALL enforce the review gate: Phase 1 spec must be approved before Phase 2 code starts.
- WHEN owner docs are built
  THE SYSTEM SHALL require that `hds-component-code` has already run and `npm run build` passes.
- WHEN a component is built
  THE SYSTEM SHALL respect existing `docs/component-conventions.md` and the semantic-token-only rule.

## Acceptance criteria

- [auto] WHEN a component process run starts
  THE SYSTEM SHALL create a per-component interview guide at `docs/component-specs/<component>/interview-guide-<YYYY-MM-DD>.md`.
  Verify: `test -f docs/component-specs/<component>/interview-guide-<YYYY-MM-DD>.md`

- [auto] WHEN Phase 1 completes for a component
  THE SYSTEM SHALL write the internal spec to `docs/component-specs/<component>/spec.md` and the API doc to `docs/api/<component>.md`.
  Verify: `test -f docs/component-specs/<component>/spec.md && test -f docs/api/<component>.md`

- [auto] WHEN the internal spec is written
  THE SYSTEM SHALL include description with do/don't usage, Base UI API surface, extension API surface, and token mapping sections.
  Verify: read the spec and grep for `## Description`, `## Usage`, `## Base UI API`, `## Extension API`, `## Token mapping`.

- [auto] WHEN the API doc is written
  THE SYSTEM SHALL NOT contain the string `Base UI` and SHALL include a props table.
  Verify: `! grep -i "base-ui\|base ui" docs/api/<component>.md && grep -q "## Props" docs/api/<component>.md`

- [auto] WHEN component code is built
  THE SYSTEM SHALL add the component to `src/components/<component>/`, pass `npm run build`, and contain no primitive or driver references.
  Verify: `test -d src/components/<component> && npm run build` exits 0 and `grep -R "hds/prim/\|hds/driver" src/components/<component>/` returns nothing.

- [auto] WHEN the Figma component is built
  THE SYSTEM SHALL produce a Figma file or section matching the spec.
  Verify: confirm Figma artifact exists in the project's Figma library and every spec state has a named match.

- [auto] WHEN owner docs are built
  THE SYSTEM SHALL produce `docs/components/<component>.mdx` with a live example for every visual axis/prop and pass `cd docs-site && npm run build`.
  Verify: `test -f docs/components/<component>.mdx && cd docs-site && npm run build` exits 0.

- [human] WHEN the API doc conventions research finishes
  THE OWNER SHALL approve the conventions doc before pilots are documented.
  Judgment owner: user.

- [human] WHEN the pilot components are done
  THE SYSTEM SHALL provide just enough context for an agent to build with them without confusion.
  Judgment owner: user, by exercising the docs with a building agent.

- [human] WHEN owner docs are reviewed
  THE SYSTEM SHALL accurately show every visual axis/prop from the spec with live examples.
  Judgment owner: user.

## Out of scope

- New components that do not originate from a Base UI primitive. (Reason: parked for a later research phase.)
- Client application build rules. (Reason: already documented in `docs/rules.md`.)
- Token system changes. (Reason: components only consume the existing token pipeline.)
- Package publishing and versioning. (Reason: not part of the component lifecycle being specced.)
